# app

Flutter app for iOS and Android. One app; each phone picks the **Main** or
**Secondary** role. License: Apache-2.0.

To install it on phones and test it, see `docs/TESTING-APPS.md`. The
`ios/` and `android/` folders were generated by `flutter create`; add the
SPDX header to any generated source file you edit.

## Status

Built (not yet tested on phones; see `docs/TESTING-APPS.md`):

- BLE pairing by QR code and control: start, stop, heartbeat with battery /
  storage / temperature, clock-sync ping/pong. Main is the BLE peripheral,
  Secondary the central (`lib/src/link/`).
- Recording through `plugins/dual_camera` in gap-free segments, white
  balance and focus locked, stabilization off, ultra-wide lens.
- Secondary keeps recording if the link drops and re-sends its segment list
  when it reconnects (for Main's screen). Uploads never need the phones
  together: Main writes `manifest.json` when it stops, naming Secondary but
  listing only its own segments, and Secondary writes `report.json` with
  its own segments (`shared/schemas/manifest.schema.json`, `docs/API.md`).
- Recordings screen with sharing, for getting test footage off the phones.
- Account linking (`lib/src/upload/account.dart`, `ui/account_screen.dart`):
  scan the website's `opensportsball://link?...` QR code, or type the
  8-character code once the phone knows the API from an earlier link. The
  device token is kept with `flutter_secure_storage` (Keychain / Android
  Keystore). "Unlink this phone" only forgets it locally. Only Main needs
  linking: when a Secondary pairs, Main gets a recording grant for it
  (`POST /games/{gameId}/grants`) and sends it over Bluetooth (`GrantMsg` /
  `GrantAck`), retrying every 30 s while it has no internet. Secondary keeps
  it in secure storage, one per game, and uploads that game's footage into
  Main's account with it. Its own account link, if any, is untouched, so a
  phone can be Main for its owner and Secondary for anyone. Main's manifest
  names Secondary only if Secondary confirmed the grant.
- Upload queue (`lib/src/upload/upload_service.dart`, `ui/uploads_screen.dart`),
  following `docs/API.md`: oldest stopped recording first, Main uploads
  `manifest.json` (Secondary: `report.json`), writing it first if it is
  missing, then each of this phone's segments as an S3 multipart
  upload (part size from the server, 64 MiB; parts streamed from disk).
  Progress is saved per recording in `upload.json` next to `recording.json`
  (format in `upload_state.dart`), so an upload resumes after a restart
  using that file plus the server's `completedParts`. Expired URLs are
  re-requested, network and 5xx errors back off from 5 s to 10 min, and a
  401 on the device token stops this phone's Main recordings until it is
  linked again (a 401 on a grant stops only that game's). Each recording
  uploads with its own credential: Main recordings with the device token,
  Secondary recordings with the game's grant; without one they wait. Uploads pause while
  this phone is recording, wait for Wi-Fi by default ("Upload on Wi-Fi
  only", with a one-time "Upload now using mobile data"), and keep the
  screen awake while sending.

Not built yet:

- **Background upload.** The queue runs only while the app is open (in the
  foreground). Uploading with the app closed needs WorkManager (Android,
  with a foreground-service notification for long transfers) and a
  background `URLSession` (iOS), handing parts to the OS. The state in
  `upload.json` is designed so a background worker can pick up the same
  queue.
- Recordings the app was killed in the middle of are recovered at the next
  launch (`AppStore.recoverInterruptedRecordings`); the upload queue writes
  their manifest or report, so they upload and process like any other.

## Layout

| Path | What |
|---|---|
| `lib/src/protocol/` | Messages, BLE framing, clock-offset estimation |
| `lib/src/link/` | `PeerLink` interface and its BLE implementation |
| `lib/src/session/` | Recorder, Main and Secondary controllers |
| `lib/src/storage/` | Identity, settings, recordings on disk, manifest builder |
| `lib/src/upload/` | Account linking, network monitor, upload queue |
| `lib/src/ui/` | Screens |
| `plugins/dual_camera/` | Native camera plugin; contract in `CHANNEL.md` |

`flutter test` runs the protocol tests, an end-to-end session test with
fake cameras and an in-memory link, and the linking / upload queue tests
against a fake API and S3 (`test/upload_fakes.dart`).
